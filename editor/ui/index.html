    Fields

    A field is a placeholder in a signature, @@givenName, filled with the user's value when the add-in inserts it. The add-in reads the values from Microsoft Graph, the user's own profile in Entra ID. AD attribute is for the preview here, read from Active Directory.

    FieldPlaceholderAD attributeGraph sourceSample value
    Without a Graph source a field stays empty in Outlook. Graph knows no description, homePhone or info. To use them, sync them from AD with Entra Connect, either into onPremisesExtensionAttributes.extensionAttribute1…15 (Exchange attributes) or as directory extensions (extension_<appId>_description), and enter that path here.

    Add-in

    Behaviour

    Where the users' values come from

    With AD, the editor exports every active user with a mail address on Publish, into users\ in the OSign folder: one small file per person with their fields and groups. The add-in reads only the file of whoever writes. To keep the values current without publishing, let Windows run the export, e.g. nightly, on a PC in the domain: powershell -ExecutionPolicy Bypass -File OSign.ps1 -ExportUsers

    Sign-in and permissions

    The add-in signs in through Outlook (no password asked) and reads, with each user's own rights, their details and groups from Entra ID and the signatures from the OSign folder in SharePoint. It uses one app registration, set in Settings → Outlook add-in, when the add-in's files are made - not in the signatures. How to register it

    Install

    The add-in's manifest, for the Microsoft 365 admin center (Settings → Integrated apps → Upload custom apps), is manifest.xml where the add-in is served, e.g. https://osign.contoso.com/manifest.xml. Settings → Outlook add-in makes the files.

    Users

    The values the signatures take from Active Directory, as they would go out. Read from AD reads them now; nothing is written yet. Publish then writes exactly what was read here - nothing you have not seen.

    Settings

    Step by step through the SharePoint folder, the app registration and the add-in.

    In SharePoint, open the document library of your home site (https://<tenant>.sharepoint.com), make a folder OSign, and choose Sync (or Add shortcut to My files). It then appears in File Explorer; its path goes in the first field. Publishing writes signatures.json and assets\ there; the photos go in photos\, by hand.

    Outlook add-in

    The add-in's files go on an HTTPS web server of your own (your web server, Azure Static Web Apps, …): they are only code, the signatures stay in SharePoint. This makes them for your server; copy the folder there and upload its manifest.xml in the Microsoft 365 admin center.

    Publish

      Image

      PNG, JPG or GIF, at most 1 MB. It is published with the signatures.

      OSign puts the company's signatures into every mail: in classic and new Outlook, and on the web. This assistant sets it up in six steps and says, for each one, what to do outside OSign. You can stop at any time and go on later: Settings → Setup assistant.

      What you need

      • A Microsoft 365 admin account: for the app registration and to give everyone the add-in.
      • A folder in SharePoint for the signatures. Step 1 makes it.
      • A place on the web for the add-in's files, e.g. Cloudflare Pages: free, no credit card.
      • About an hour. Afterwards, the add-in takes up to a day to reach every Outlook.

      The signatures, their images and the photos live here. Outlook reads them with each user's own sign-in; nothing goes anywhere else.

      Upload them

      https://dash.cloudflare.com → Workers & Pages → Create → Pages → Upload assets. A project name (e.g. company-osign), drag in the folder's content, Deploy. Your own domain: project → Custom domains. Later versions: Create new deployment, upload again. The file _headers makes updates arrive within minutes.

      Azure portal → Create a resource → Static Web App, plan Free, deployment source Other. Manage deployment token, copy it. Then in PowerShell (needs Node.js): $env:SWA_CLI_DEPLOYMENT_TOKEN='<token>'; npx @azure/static-web-apps-cli deploy <folder> --env production

      Upload the folder's content by FTP/SFTP into the directory of the (sub)domain, with HTTPS switched on at the host. Include .htaccess: some FTP programs hide files starting with a dot.

      Copy the folder's content into the site or a virtual directory with HTTPS. Its web.config sets the caching; if IIS then answers with error 500, that section is locked on the server: delete web.config.

      Copy the folder's content there. Have the server send Cache-Control: no-cache (nginx: add_header Cache-Control no-cache;), so updates arrive within minutes.

        Register the add-in in Entra ID

        1. Entra admin center → App registrations → New registration. Name: OSign. Accounts: this organizational directory only (then enter the tenant ID too, in Settings → Outlook add-in).
        2. Authentication → Add a platform → Single-page application, redirect URI brk-multihub://<host the add-in is served from>, e.g. brk-multihub://osign.contoso.com.
        3. API permissions, Microsoft Graph, delegated: User.Read, Sites.Read.All (the OSign folder) and, for signatures by AD group, GroupMember.Read.All. Then Grant admin consent, so no user is asked.
        4. The Application (client) ID goes into Settings → Outlook add-in; then Make the add-in files and copy them to the web server.
        5. The OSign folder has to be readable for everyone who signs: in SharePoint, share it (read) with all employees.

        Import templates

        Pick a folder, or the template files (.htm) together with their images. The images a template uses (images/logo.png) are found among what you pick by their file name and become part of the signatures. Templates from CI-Sign and from classic Outlook (%APPDATA%\Microsoft\Signatures) work.
