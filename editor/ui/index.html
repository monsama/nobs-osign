    Fields

    A field is a placeholder in a signature, @@givenName, filled with the user's value when the add-in inserts it. The add-in reads the values from Microsoft Graph, the user's own profile in Entra ID. AD attribute is for the preview here, read from Active Directory.

    FieldPlaceholderAD attribute Graph source Sample value
    Without a Graph source a field stays empty in Outlook. Graph knows no description, homePhone or info. To use them, sync them from AD with Entra Connect, either into onPremisesExtensionAttributes.extensionAttribute1…15 (Exchange attributes) or as directory extensions (extension_<appId>_description), and enter that path here.

    Add-in

    Behaviour

    Where the users' values come from

    With AD, the editor exports every active user with a mail address on Publish, into users\ in the OSign folder: one small file per person with their fields and groups. The add-in reads only the file of whoever writes. To keep the values current without publishing, let Windows run the export, e.g. nightly, on a PC in the domain: powershell -ExecutionPolicy Bypass -File OSign.ps1 -ExportUsers

    Sign-in and permissions

    The add-in signs in through Outlook (no password asked) and reads, with each user's own rights, their details and groups from Entra ID and the signatures from the OSign folder in SharePoint. It uses one app registration, set in Settings → Outlook add-in, when the add-in's files are made - not in the signatures. How to register it

    Settings

    In SharePoint, open the document library of your home site (https://<tenant>.sharepoint.com), make a folder OSign, and choose Sync (or Add shortcut to My files). It then appears in File Explorer; its path goes in the first field. Publishing writes signatures.json and assets\ there; the photos go in photos\, by hand.

    Outlook add-in

    The add-in's files go on an HTTPS web server of your own (your web server, Azure Static Web Apps, …): they are only code, the signatures stay in SharePoint. This makes them for your server; copy the folder there and upload its manifest.xml in the Microsoft 365 admin center.

      OSign manages your organisation's email signatures centrally and adds them automatically to every message in classic Outlook, new Outlook and Outlook on the web. This assistant guides you through the one-time setup. Each step explains what to do in Microsoft 365 and saves your entries right away, so you can pause at any time and continue later under Settings → Setup assistant.

      Before you start

      • Microsoft 365 administrator rights – for the app registration in Entra ID and for deploying the add-in.
      • Access to SharePoint – step 1 creates a folder for the signatures.
      • A web host for the add-in's files – for example Cloudflare Pages: free of charge, no credit card required.
      • About one hour. After deployment, Microsoft 365 can take up to 24 hours to make the add-in available in every mailbox.

      OSign keeps the signatures, their images and the photos in a folder in your company's SharePoint, where Outlook reads them with each user's own sign-in. Make a folder OSign there (with a folder photos in it), and tell OSign which one. This is not the folder you unpacked OSign itself into.

      Placeholders such as @@givenName or @@mobile are replaced with the sender's details. Choose where these details come from:

      You can change this at any time under Add-in. Reading from Active Directory requires this PC to be joined to the domain.

      The add-in consists of a few static files – code only, no data – that Outlook loads from a web address. They only change with a new version of OSign. Choose where they will be hosted:

      Requirements: HTTPS with a trusted certificate, reachable from the internet (Outlook loads the files on each user's device), and no sign-in in front of the files. Tip: an address on your own domain, e.g. osign.<company>.ch as a CNAME to the host, lets you change the host later without touching Microsoft 365.

      The add-in signs in through Outlook with single sign-on; users are never asked for a password. For this it needs an app registration in your tenant.

      What to do

      1. Register the app. Open https://entra.microsoft.com → App registrations → New registration. Name: OSign. Supported account types: Accounts in this organizational directory only. Select Register.
      2. Add the redirect URI. Authentication → Add a platform → Single-page application, with this URI:
      3. Grant the permissions. API permissions → Add a permission → Microsoft Graph → Delegated permissions: . Then select Grant admin consent, so that no user is prompted.
      4. Copy the IDs. On the Overview page, copy the Application (client) ID and the Directory (tenant) ID into the fields below.

      No client secret or certificate is needed. If the add-in's address changes later, add the new redirect URI as well.

      OSign now generates the add-in's files for your address, app registration and SharePoint folder, and saves them in a folder on this PC.

        2. Choose Office Add-in and Provide link to the manifest file:
        3. Assign users: for testing Just me or a pilot group, later the entire organisation.

        The setup is complete. Next, create your signatures: import your existing templates (from CI-Sign or classic Outlook) or start a new one, define who receives which signature, and select Publish. Changes to signatures never require new add-in files.

        Register the add-in in Entra ID

        1. Entra admin center → App registrations → New registration. Name: OSign. Accounts: this organizational directory only (then enter the tenant ID too, in Settings → Outlook add-in).
        2. Authentication → Add a platform → Single-page application, redirect URI brk-multihub://<host the add-in is served from>, e.g. brk-multihub://osign.contoso.com.
        3. API permissions, Microsoft Graph, delegated: User.Read, Sites.Read.All (the OSign folder) and, for signatures by AD group, GroupMember.Read.All. Then Grant admin consent, so no user is asked.
        4. The Application (client) ID goes into Settings → Outlook add-in; then Make the add-in files and copy them to the web server.
        5. The OSign folder has to be readable for everyone who signs: in SharePoint, share it (read) with all employees.

        Import templates

        Pick a folder, or the template files (.htm) together with their images. The images a template uses (images/logo.png) are found among what you pick by their file name and become part of the signatures. Templates from CI-Sign and from classic Outlook (%APPDATA%\Microsoft\Signatures) work.

Example: Mobile: @@mobile disappears for someone without a mobile number, instead of showing «Mobile:» with nothing after it. Lines without placeholders always stay. Works for paragraphs, line breaks and table rows.
          The signature is offered only to members of at least one of these groups. Members of nested groups count too: someone in «SG-Sales-Zurich», itself a member of «SG-Sales», gets the signature for «SG-Sales». Enter the group names as in Active Directory, separated by commas. With values from Entra ID only, the groups must be synchronised to Entra ID and the app needs GroupMember.Read.All.
          The signature is offered only to users whose department attribute is one of these, compared as a whole and regardless of capitals: Sales matches «sales», but not «Sales Europe». Separate several with commas.
          The signature is used only when the message is sent from an address in one of these domains, e.g. example.com for anna@example.com. Useful for shared mailboxes or several companies in one tenant. A subdomain such as mail.example.com has to be listed itself.
          The attribute's name in Active Directory (the lDAPDisplayName, as in Attribute Editor), e.g. telephoneNumber or extensionAttribute1. Used for the preview, and for what the add-in shows when the values come from Active Directory.
          Where the add-in finds the value in Entra ID, as Microsoft Graph names it, e.g. mobilePhone, onPremisesExtensionAttributes.extensionAttribute1 or extension_<appId>_description. Leave it empty for fields Entra ID does not have; with Entra ID and Active Directory they then come from AD.
          Outlook may insert the user's own signature as well (from Outlook's own signature settings). When this is on, the add-in switches it off in every message it signs, so no mail ends up with two. Users' own signatures are not deleted.
          When this is on, users can pick another signature in the add-in's pane (OSign → Signatures), for new mail and for replies separately, from the ones they are allowed. When it is off, everyone gets the default, and the pane only inserts.
          If the user's details cannot be read (offline, sign-in not yet possible), the add-in normally inserts nothing and tries again with the next message. When this is on, it inserts the signature anyway, with empty fields; only the mail address is filled in. Lines with empty fields are left out as usual.
          Decides where the add-in reads each sender's details. Entra ID needs nothing exported but lacks some AD attributes. Active Directory values are exported to SharePoint when you publish (and, if set up, by a scheduled task); you review them first under Users. Groups for Who gets it come from the same source.
